# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev       # Start dev server (Next.js, http://localhost:3000)
npm run build     # Production build (runs `prebuild` first); validates typing
npm run start     # Serve the production build
npm run lint      # ESLint (eslint-config-next: core-web-vitals + typescript)
npm test          # Vitest — resolveCv + the adapter contract suite
npm run test:e2e  # Playwright — three tripwires, builds and serves first
npm run snapshot  # Regenerate src/content/snapshot.json by hand
```

Tests are deliberately narrow. Vitest covers the two modules that can fail
*silently* — `src/lib/cv/resolve.ts` and the `ContentSource` contract. Playwright
covers only what unit tests structurally cannot: print pagination and route
gating against a real build. There are intentionally no component or snapshot
tests; see "Testing" below. Everything else is verified with `npm run build` and
by viewing the dev server.

## Stack

Next.js 16 (App Router) · React 19 · TypeScript · Tailwind CSS v4 · shadcn/ui · Framer Motion. Deployed on Vercel (`@vercel/analytics` is wired into the root layout).

## Architecture

This is a single-page personal portfolio plus shareable CV pages. Content is **data-driven** and reached through one boundary. To change what the site says, edit data files — not components.

### The content port — read this before touching content

`src/lib/content/` is the **only** place that knows where content lives. Nothing outside it may import `src/data/*` or, later, a CMS client. Adapters behind it are interchangeable:

| Adapter | Source | Role |
|---|---|---|
| `adapters/files.ts` | `src/data/*.ts` | Default today; the seed after a CMS lands |
| `adapters/snapshot.ts` | `src/content/snapshot.json` | Runtime fallback, regenerated by `prebuild` and committed |
| `adapters/payload.ts` | — | Stage 2, not yet built |

`CONTENT_SOURCE=files|snapshot|payload` picks one. `contract.test.ts` is one suite run against every adapter — a new adapter must pass it unchanged. **`src/content/snapshot.json` is generated; never hand-edit it.**

- **Content layer** (`src/data/`): `profile.ts` (typed `Profile`), `projects.ts`, `education.ts`, `workExperience.ts`, `voluntary.ts`, `certifications.ts`, `references.ts`, `leadership.ts`, `cvVariants.ts`. Shapes live in `src/types/index.ts`; CV-specific shapes in `src/types/cv.ts`. `ExperienceGroup` nests `roles[]` so one organisation can list multiple roles; the port flattens this into `ExperienceItem[]` for CVs.
- **`key` is a permanent contract.** Every project, role, education entry, certification, reference and project link carries a `key`. CV variants target items by it — renaming one silently orphans every override pointing at it. It is `key` and not `id` because Payload reserves `id`.
- **Home page** (`src/app/page.tsx`): an async server component that reads the port and passes content down. `HeroSection` is a client component and receives `profile` / `styledCv` / `atsCv` as props.
- **Project detail pages** (`src/app/projects/[slug]/page.tsx`): statically generated per project via `generateStaticParams()` over the `projects` array. Slug order in `projects.ts` also drives prev/next navigation. `fullDescription` is split on `\n\n` into paragraphs — author multi-paragraph copy with double newlines.
- **Component tiers** (`src/components/`): `sections/` (page sections) → `shared/` (reusable pieces like `ProjectCard`, `TagBadge`, `SectionHeading`) → `ui/` (unmodified shadcn primitives). `layout/` holds `Navbar` and `Footer` (rendered by the root layout, not the page).

## CVs

One content pool, many outputs. A **variant** (`src/data/cvVariants.ts`) is a recipe, not a copy.

**Resolution is three tiers**, and this ordering is the whole design:

1. **Canonical item** — the data file record.
2. **Format layer** — `showInAtsCv` / `showInStyledCv` and the `atsCvUrls` / `styledCvUrls` checklists. These are per-format defaults and they are *kept*, not superseded: the same project can appear on the ATS CV but not the styled one, with different links on each.
3. **Variant layer** — only for items a variant explicitly lists. Everything unlisted behaves exactly as tier 2 says, so a variant that lists nothing renders exactly what the flags alone produce.

`resolveCv(content, variant)` in `src/lib/cv/resolve.ts` does this and is **pure** — no I/O, no clock, no mutation. Keep it that way; it is the one piece of logic here that fails silently when wrong.

- `featured` is **site-only** (homepage grid). It is deliberately not a CV gate — it used to act as an undocumented third filter on the styled CV.
- URL checklists are ordered arrays: omit for all available URLs, `[]` for none. `link:<key>` addresses an entry in `links[]`.
- **Renderers are presentational.** `CvStyledDynamic` and `CvAtsDynamic` take one `ResolvedCv` prop, import no data, and contain no filtering.
- **Publishing**: exactly one variant per format may be `published`. `/cv/styled` and `/cv/ats` are stable aliases resolving to whichever that is, so shared links survive republishing.

### Privacy — do not regress these

Unpublished variants are author-only. Four leak vectors are closed on purpose:

1. **No `generateStaticParams` on `/cv/[variant]`** and `dynamic = "force-dynamic"`. Prerendering would bake private slugs into the build manifest and ship private CVs to the CDN.
2. **`sitemap.ts` emits only the two aliases** — never map over `getCvVariants()`.
3. **No `opengraph-image.tsx` under `cv/[variant]`.** It is an independently routable segment that would not inherit the page's gating.
4. **The download route repeats the auth check** — route handlers inherit nothing from the page.

Unauthorised access returns **404, never 403**: a 403 confirms the slug exists. `isAuthor()` in `src/lib/auth.ts` is the single seam (signed cookie now, `payload.auth` later).

## Theming / styling conventions

All design tokens are CSS custom properties in `src/app/globals.css` and are the single source of truth for color, radius, and spacing.

- The site is **dark-theme only** by design (a `@layer base` reset forces it). Tokens live under `:root` as `--bg-*`, `--text-*`, `--accent-*`, `--radius-*`.
- Components style with **inline `style={{ color: "var(--text-primary)" }}`** referencing these variables, rather than Tailwind color classes. Match this pattern when editing components — the existing code leans on `var(--…)` heavily.
- Tailwind v4 is configured in CSS (`@theme inline` in `globals.css`), not a `tailwind.config.js`. Tokens are also forwarded to shadcn-style names (`--color-*`) there.
- The CV is an intentional exception: `.cv-root` in `globals.css` overrides the tokens to a **light** theme and adds print styles for A4 export. `CvAtsDynamic` (`@react-pdf/renderer`) is a parallel *rendering* of the same resolved content — the content itself is no longer duplicated, so there is nothing to keep in sync by hand.
- **`.cv-print-scope` marks the subtree that reaches the printer.** `@media print` hides everything outside it, so it must be applied at *both* render sites — the hidden portal in `HeroSection` and the standalone `/cv/[variant]` page. Omitting it on the standalone page makes printing the shareable link produce a blank sheet.
- **Multi-page CVs are fine; unsafe breaks are not.** `break-inside: avoid` is on `.cv-entry` (each atomic block) rather than whole sections, and vertical margin comes from `@page` so it repeats on every sheet rather than only the first.
- `CvStyledStatic.tsx` is a **frozen break-glass fallback** behind `CV_FALLBACK_STATIC=1`, not a live component. It is the only CV that depends on no data source at all. Do not hand-edit it to match content changes — that re-creates the duplication this architecture removed.
- `src/data/references.ts` holds CV referees. Rendered only inside the CV renderers (last section, after Leadership & Comm.), never on the live site, and always without contact details — "available upon request" is noted once instead. Modern CVs often omit the section entirely, so don't be surprised if this changes shape.
- Reusable helpers in `globals.css`: `.section` / `.section-container` (layout), `.tag`, `.card-glow` (hover glow), `.dot-grid` (hero background).

## Fonts

Loaded via `next/font/google` in the root layout: **Syne** → `--font-display` (headings, `.font-display`), **DM Mono** → `--font-body` (body/mono, `.font-mono`). The body default is monospace by design.

## Placeholder content

Some content still contains template placeholders (e.g. `[YOUR NAME]` in project-page metadata, `[PLACEHOLDER]` comments in `projects.ts`). When editing, prefer replacing placeholders with real profile data from `src/data/profile.ts` rather than leaving them.

## Testing

Two suites, both deliberately scoped.

- **Vitest** (`src/**/*.test.ts`) — `resolveCv` tier semantics and the adapter contract. Both are pure functions over plain data, and both survive a CMS migration unchanged, which is what makes them the evidence such a migration was faithful. Write `resolveCv` changes test-first.
- **Playwright** (`tests/e2e/`) — three tripwires only: print pagination, unpublished-variant gating, and sitemap contents. Builds and serves the app first.

Deliberately **not** tested, so these are decisions rather than gaps:

| | Why |
|---|---|
| Visual regression / screenshots | CV output changes on purpose; baselines would churn |
| CV components via Testing Library | Asserts JSX shape on components meant to change |
| `generateStaticParams` slug leakage | Neither tool sees the build manifest — inspect `npm run build` output by hand |

## Conventions

- Path alias `@/*` → `src/*`.
- Icons come from two libraries: `lucide-react` and `@phosphor-icons/react` (import Phosphor server icons from `/dist/ssr`; the package is in `optimizePackageImports`).
- Use `cn()` from `src/lib/utils.ts` (clsx + tailwind-merge) to compose class names.
